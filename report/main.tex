\section{Introduction (Christophe ElChabab, Joey Saade)}
\label{sec:introduction}
\textbf{Project overview.} A reported security problem needs more than a description: the team must know which asset is affected, who is investigating it, what has already been done and whether the issue is resolved. Our backend keeps those records together and controls who can read or change them.

The system covers the nine services in the Sprint I handout. Employees report incidents, analysts investigate assigned incidents, administrators manage records and assignments, and auditors review the information without changing it. Threat indicators and vulnerabilities give context to investigations. Notifications, audit records and reports make the resulting activity visible to the appropriate users.

\textbf{Scope and objectives.} This sprint is backend-only; there is no frontend application. It extends the API, database, documentation and Git work from the earlier labs into a team project. Our main objectives are to:
\begin{itemize}
\item provide the required REST endpoints with each owner's full name in the route;
\item store related records with primary keys, foreign keys and validation checks;
\item authenticate callers and enforce both role and record-level permissions;
\item test valid requests, invalid input and forbidden operations in Postman;
\item demonstrate service integration and record each member's work in Git.
\end{itemize}

\section{System Architecture (Christophe ElChabab, Joey Saade, Karl Khouri)}
\label{sec:architecture}
\textbf{Overall design.} Each service is a separate FastAPI process with its own HTTP port. The local implementation uses one SQLite file so references to users and assets remain consistent across the services. Services also communicate over HTTP: they deliver audit events and notifications, and the Reports service calls the other services' list APIs. This is a shared-database local design, not nine independently deployed databases.

\textbf{Communication between services.} Users log in through Joey's Users service. The returned bearer token is sent with protected requests. A change that needs an audit entry or notification first saves that event in the \code{outbox} table together with the record change. After the transaction commits, delivery calls the destination API. If delivery fails, the saved event can be retried. A unique event ID prevents a retry from creating a second logical event.

Karl's reports request lists from the owning APIs using the caller's token. For example, the vulnerability report uses Christophe's vulnerability list rather than directly counting his table. This keeps access checks at the service boundary and makes a failed source visible instead of reporting a misleading zero.

\section{Database Design (Christophe ElChabab, Joey Saade, Karl Khouri)}
\label{sec:database}
\textbf{Design decisions.} One shared SQLite file holds identity and asset records referenced by the other services. Every main entity has an integer primary key. Foreign keys stop a record from referring to a missing user, asset, incident or playbook. CHECK constraints limit status/severity values and CVSS ranges; unique constraints prevent duplicate usernames, threat indicators and playbook step numbers.

The three schema diagrams below divide the database by service ownership while repeating shared tables where necessary. Arrows point from the table holding a foreign key to the table it references. The actual field definitions are available in the linked \repolink{joey/schema.sql}{Joey schema}, \repolink{christophe/schema.sql}{Christophe schema} and \repolink{karl/schema.sql}{Karl schema}.

\section{Error Handling and Validation (Christophe ElChabab, Joey Saade, Karl Khouri)}
\label{sec:validation}
\textbf{Error handling approach.} Requests are checked before a change is written. A failed operation returns a useful status and JSON message rather than a successful response with missing data. The shared response format is:
\begin{lstlisting}
{"status": "error", "message": "..."}
\end{lstlisting}
This is the response format, not a captured execution. Field-validation errors can also include an \code{errors} array. Actual rejected requests are shown in the evidence appendices.

\begin{small}\begin{tabularx}{\linewidth}{@{}p{16mm}p{35mm}X@{}}
\toprule\textbf{HTTP} & \textbf{Meaning} & \textbf{Example handled by the backend}\\\midrule
401 & Authentication required & Incorrect password; absent, invalid or expired token; invalid audit service key.\\
403 & Permission refused & Employee reading threats; auditor updating a vulnerability; unassigned analyst changing an incident.\\
404 & Record not found & Unknown user, asset, threat, vulnerability, incident, audit entry or playbook.\\
409 & Conflicting operation & Duplicate indicator, referenced deletion, duplicate step number or skipped lifecycle state.\\
422 & Invalid input & Invalid email/IP/CVE/CVSS, missing fields, unknown asset, invalid assignee or malformed date.\\
502/503 & Report source failure & An upstream API returns unusable data or cannot be reached.\\\bottomrule
\end{tabularx}\end{small}

\textbf{Validation rules.} Users require a valid email, unique username and a password meeting the configured length/content rules. Assets require valid IP, type, criticality and status values. Threats validate their value according to indicator type and reject duplicate normalized indicators. Vulnerabilities validate CVE syntax, CVSS in 0--10 and the affected asset. Boolean CVSS/IDs, empty updates and unknown body fields are rejected in Christophe's services. Incidents and response actions enforce the workflows in Figure~\ref{fig:workflows}.

\textbf{Security checks.} SQL values are passed as bound parameters, not joined into query text. The server chooses permitted filter columns and checks role/ownership before returning a record. Role changes cannot be requested through public registration or ordinary profile updates. Audit actors and investigation-note authors come from authenticated identity, so a request cannot simply name another author. Forbidden requests are recorded by the audit integration.

\textbf{Checking the result against the database.} In Christophe's populated run, the stored records and reports agree on two Critical threats, two vulnerabilities and three incidents. One vulnerability is Closed/Critical at 9.1 and the other is Open/Medium at 5.0, giving mean CVSS 7.05. Incident 1 is Closed/High; the other two are Open/Critical and Open/Medium. Later Cleanup screenshots show deletion of the test threats/vulnerabilities, so those later responses are not inconsistent with the earlier populated database images.

\section{Authentication and Authorization (Christophe ElChabab, Joey Saade, Karl Khouri)}
\label{sec:authorization}
\textbf{Authentication mechanism.} Passwords are stored as salted PBKDF2-SHA256 hashes, not plaintext. Login verifies the password and issues a signed bearer token valid for one hour. Each protected request verifies the signature/expiry and reloads the current user, so a deleted, inactive or suspended account loses access. Service-to-service audit/notification calls use distinct private keys instead of a user's password.

\begin{small}\begin{tabularx}{\linewidth}{@{}p{34mm}X@{}}
\toprule\textbf{Role} & \textbf{Access in the implementation}\\\midrule
Security Administrator & Manages users, assets, assignments, threats and vulnerabilities; reviews audits/reports and manages response playbooks. Destructive operations still respect referenced-record and workflow checks.\\
Security Analyst & Investigates assigned incidents and adds notes; reads threat information and updates vulnerabilities; works on permitted response actions. Does not gain administrator deletion rights.\\
Regular Employee & Manages their own profile, reports incidents, views only their submitted incidents and handles their own notifications. Cannot browse threat/vulnerability records or organizational assets.\\
Security Auditor & Reads permitted users, assets, incidents, threats, vulnerabilities, audit records and reports without mutating them.\\\bottomrule
\end{tabularx}\end{small}

\textbf{Record-level permissions.} The professor clarified that auditors may search threats and that all four roles may call \code{GET /incidents}. Administrators/auditors see all incidents, analysts see their assignments and employees see their submissions. These restrictions use the token's user ID even if a request supplies misleading reporter, assignee or role query parameters. The same principle limits notifications to their recipient where required.

The shared login evidence in Appendix~\ref{app:christophe} shows both a valid administrator login and an incorrect password returning 401. Employee threat access returns 403 while an allowed reader succeeds; auditor vulnerability updates and unauthorized incident changes are rejected. Joey's runner summary and Karl's protected API captures provide additional access-control evidence. The handout's two permission clarifications are applied in the endpoint tables above.

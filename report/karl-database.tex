Karl Khouri's four tables are defined in \texttt{karl/schema.sql} and created after the users table they reference; the Reports service stores no tables. All use integer primary keys. \texttt{audit\_logs}, \texttt{playbooks} and \texttt{response\_actions} use AUTOINCREMENT, so a deleted entry's ID is never given to a new row. Deletion records, execution history and notification event IDs keep pointing at the right record. Databases created before this change are rebuilt on startup with their rows kept.

\texttt{audit\_logs} stores one row per event with a unique \texttt{event\_id}. \texttt{actor\_user\_id} references \texttt{users.id} with ON DELETE SET NULL, while \texttt{original\_actor\_user\_id} and \texttt{actor\_label} keep the actor after the account is deleted. CHECK constraints limit severity to Information, Warning, Error and Critical and the source to service, user or audit. Indexes on the original actor and the occurrence time support user activity lookups and date-range searches. The \texttt{audit\_logs\_immutable} trigger aborts any UPDATE except that foreign-key nulling.

\texttt{playbooks} has a case-insensitive unique name, category and severity CHECK constraints, and \texttt{created\_by} referencing \texttt{users.id}. \texttt{response\_actions} references \texttt{playbooks.id} with ON DELETE CASCADE and \texttt{users.id} through \texttt{assigned\_to} and \texttt{completed\_by}. Its status is limited to Pending, In Progress and Completed, and \texttt{UNIQUE(playbook\_id, step\_order)} prevents two steps sharing a number. \texttt{action\_history} references the action, playbook and changing user with ON DELETE SET NULL. It also stores the original action and playbook IDs, so the execution history survives deletion. One playbook has many response actions, one action has many history rows, and one user can create many playbooks, be assigned many actions and appear in many audit entries. A user who created a playbook or is assigned a step cannot be deleted while those references remain.
